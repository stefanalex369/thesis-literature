# rfc6749: The OAuth 2.0 Authorization Framework

- **Reference:** Hardt, D. (Ed.) (2012). *The OAuth 2.0 Authorization Framework* (RFC 6749). Internet Engineering Task Force.
- **Full text:** free standard, read online at https://www.rfc-editor.org/rfc/rfc6749 (not copied here; the official text stays the reference)
- **Topic:** API authorization
- **Thesis chapters:** 3 (API integration), 5 (Security)

## What it is

The standard that defines OAuth 2.0: the roles (resource owner, client, authorization server, resource server), access tokens, refresh tokens and the grant types for obtaining tokens.

## What is relevant for my work

- **Server-to-server access.** My application calls external APIs on behalf of the organization, with no user present. In RFC 6749 this is the client credentials grant (section 4.4). Section 4.4.3 states that no refresh token should be issued in this case: when the access token expires, the client simply requests a new one with its credentials.
- **Zoom.** Server-to-Server OAuth apps follow this pattern with Zoom's own `account_credentials` grant type: the application stores the account ID, client ID and client secret on the server, requests a short-lived access token, reuses it until shortly before it expires and then requests a new one. The advantage over a static token is not that no secret is stored (one is), but that the secret is sent only to the token endpoint, while API calls carry a token that expires quickly.
- **Comparison with Moodle.** Moodle web services use a long-lived token, sent with every call. I will compare the two approaches in the security chapter (lifetime, revocation, exposure).
- **Section 10 (Security Considerations)** requires keeping client credentials confidential and using TLS. In my application, credentials are read from the server's environment or a secrets file outside the repository.

## Limitations

OAuth covers authorization for API access only. User login to my own application is a separate concern, covered by owasp2025 (A07).
